Every `act` subcommand accepts the same three forms of reference: a local path, an HTTP(S) URL,
or an OCI registry ref. We'll use the published SQLite component at `actpkg.dev/library/sqlite`.

## Inspect

```bash
act info actpkg.dev/library/sqlite --tools
```

Prints the component's metadata (`name`, `version`, `description`), its declared capabilities,
and every tool it exposes.

## Call a tool directly

```bash
mkdir -p /tmp/actdemo

act call actpkg.dev/library/sqlite query \
  --args '{"sql": "SELECT sqlite_version()"}' \
  --session-args '{"database_path": "/tmp/actdemo/app.sqlite"}' \
  --grant '{"wasi:filesystem":{"mode":"allowlist","allow":[
      {"path":"/tmp/actdemo/**","mode":"rw"},
      {"path":"/dev/urandom","mode":"ro"}]}}'
```

```json
[
  {
    "sqlite_version()": "3.51.3"
  }
]
```

`act call` instantiates the component, runs one tool, prints the result, and exits.

Two things in that command are worth unpacking:

- **`--session-args`** — `sqlite` is a stateful component: it holds an open database connection,
  so it exports `session-provider` and takes its connection parameters at session open rather
  than per call. On `act call`, this flag opens a session-of-1, runs the call, and closes it.
  Ask any component what it accepts with `act session open-args-schema <component>`.
- **`--grant`** — the component declares a `wasi:filesystem` capability, and nothing reaches the
  filesystem until you grant it. Note the grant covers the whole directory and `/dev/urandom`,
  not just the database file: SQLite also writes a `.lock` sidecar and reads random bytes. Grant
  too little and the audit trail tells you exactly what was refused.

## Serve it to an agent

<Tabs syncKey="transport">
<TabItem label="MCP over stdio">
```bash
act run actpkg.dev/library/sqlite --mcp \
  --session-args '{"database_path": "/tmp/actdemo/app.sqlite"}' \
  --grant '{"wasi:filesystem":{"mode":"allowlist","allow":[
      {"path":"/tmp/actdemo/**","mode":"rw"},
      {"path":"/dev/urandom","mode":"ro"}]}}'
```
Exposes the component over MCP stdio. Plug into Claude Code, Claude Desktop, Cursor, or any MCP
client. With `--session-args` the host pre-opens one session and hides the session machinery
from the client entirely.
</TabItem>
<TabItem label="MCP over HTTP">
```bash
act run actpkg.dev/library/sqlite --mcp --http -l "[::1]:3000" \
  --session-args '{"database_path": "/tmp/actdemo/app.sqlite"}' \
  --grant '{"wasi:filesystem":{"mode":"allowlist","allow":[
      {"path":"/tmp/actdemo/**","mode":"rw"},
      {"path":"/dev/urandom","mode":"ro"}]}}'
```
The same MCP server on an HTTP listener, at `/mcp`. Use it for a remote or containerised agent.
See [Transports](/docs/host/transports/).
</TabItem>
</Tabs>

## Wire it into your agent

Rather than typing that command, put it in your MCP client's config. In Claude Code that is
`.mcp.json` at the root of the project:

```json
{
  "mcpServers": {
    "sqlite": {
      "command": "npx",
      "args": [
        "@actcore/act", "run", "actpkg.dev/library/sqlite", "--mcp",
        "--session-args", "{\"database_path\": \"/tmp/actdemo/app.sqlite\"}",
        "--grant", "{\"wasi:filesystem\":{\"mode\":\"allowlist\",\"allow\":[{\"path\":\"/tmp/actdemo/**\",\"mode\":\"rw\"},{\"path\":\"/dev/urandom\",\"mode\":\"ro\"}]}}"
      ]
    }
  }
}
```

Each flag is its own array element, and the JSON values passed to `--grant` and `--session-args`
are strings, so their quotes are escaped. If you have `act` on `$PATH`, use `"command": "act"`
and drop the leading `"@actcore/act"` argument.

The equivalent one-liner, if you would rather not edit the file by hand:

```bash
claude mcp add sqlite -- npx @actcore/act run actpkg.dev/library/sqlite --mcp \
  --grant '{"wasi:filesystem":{"mode":"allowlist","allow":[{"path":"/tmp/actdemo/**","mode":"rw"},{"path":"/dev/urandom","mode":"ro"}]}}'
```

For a component you serve over HTTP instead, point the client at the endpoint:

```json
{
  "mcpServers": {
    "sqlite": { "type": "http", "url": "http://[::1]:3000/mcp" }
  }
}
```

### Why this file is worth committing

`.mcp.json` lives in the repository, so the **grant travels with the project**. Everyone who
opens it gets the same component at the same version with the same capability ceiling — rather
than each developer running an `npx` tool with ambient access to their whole machine and hoping
it behaves. A reviewer can read the diff and see exactly what a new tool is allowed to touch.

:::caution[Don't put secrets in it]
It is a committed file. Credentials belong in the credential store, not in `env` or in
`--session-args`: run `act login <component>` once, or `act secret set`, and the component reads
them at session open. See [`act secret`](/docs/reference/cli/#act-secret).
:::

## Where did the `.wasm` go?

`act` cached it to `~/.cache/act/components/`. Subsequent runs skip the network. `act store list`
shows what's cached, `act store gc` prunes it.

## Why did the command need a grant?

The SQLite component declares a `wasi:filesystem` capability. At runtime you must grant it —
otherwise the component can open no files at all. The declaration is a **ceiling**: you can't
grant more than the component asked for, and the component can't reach past what you granted.

The default policy mode is `ask`, so an interactive run prompts you on first access instead of
requiring the flag up front. A headless run with no prompt channel degrades to deny — which is
why scripted invocations like the ones above pass `--grant` explicitly. See
[Policy & sandbox](/docs/host/policy/).
